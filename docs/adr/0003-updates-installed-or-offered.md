# Updates are installed where electron-updater can, and offered as a download elsewhere

The installed app looks for newer releases on GitHub Releases. electron-updater applies them itself only for installers it knows how to replace: the Windows NSIS installer, the AppImage, the `.deb` and the `.rpm` download an update in the background and restart into it when the user asks. macOS won't let it swap in an update to an app that isn't signed with a Developer ID, which v1 isn't, so on macOS the app asks GitHub's API for the latest release itself and, when it's newer, offers to open its download page; macOS users run the new installer by hand.

Windows ships an NSIS installer rather than an `.msi`, which the spec first asked for: electron-updater's Windows updater replaces NSIS installs only, so an MSI install could never update itself. MSI's strengths are central deployment by IT departments (Intune, ConfigMgr, Group Policy) and installs they control; Polyscope's users mostly install it themselves, so updating themselves matters more. Shipping both would mean telling the two installs apart and keeping them out of each other's install folder, so an `.msi` for managed installs is left until someone asks for it. Once the app is signed with a Developer ID (planned alongside notarization, which v1 leaves out), macOS can move to electron-updater too; it needs a `zip` target beside the `dmg` for that, which is where electron-updater gets macOS updates from.
